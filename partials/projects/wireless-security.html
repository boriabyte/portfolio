Wireless Security System

Three-node wireless security proof of concept built at a Google × Digital Stack IoT summer school with two fellow students. Three ESP32 boards, one per team member, exchange card-scan and sensor events peer-to-peer over Wi-Fi using ESP-NOW, with no access point or internet connection required, verified by testing the whole setup offline.

Stack

Arduino IDE and C++ (Arduino framework) on the ESP32 core. Radio communication uses ESP-NOW (esp_now.h) with the Wi-Fi radio in station mode; cards are read through the MFRC522 driver over SPI, with an NDEF layer (NfcAdapter) on top for reading structured card data instead of raw bytes.

System architecture

Every board is both a node and a peer: each carries its own RC522 reader and two status LEDs, so any member can scan a card and have the result reach the other two. The three boards form a full mesh, with each board registering the other two by MAC address, so there is no central controller.

Scanning an NFC card checks the access code stored on it against a shared unlock condition; a match lights the green LED and broadcasts confirmation to the other two boards, a mismatch lights red on all three. One board additionally samples the HC-SR04 proximity sensor and another carries the piezo buzzer, both broadcasting their readings as ESP-NOW packets alongside the card events, so any board's sensor state is visible to the whole mesh.

Card verification

The check is done on the reading board, one scan at a time:

  1. The main loop polls the reader; when a tag is present it is read and its type and UID are logged to the serial console.
  2. If the tag carries an NDEF message, each record's payload is read as raw bytes and turned into a string.
  3. The first three characters are dropped, which is consistent with the layout of an NDEF text record, where a status byte and a two-letter language code precede the actual text.
  4. The remainder is parsed as an integer and compared against the shared access code compiled into the firmware.
  5. A match lights the accepted-card LED for 1.5 s, anything else lights the rejected-card LED for the same time.
  6. Either way, the parsed value is sent to the other boards, so accepted and rejected scans are both visible mesh-wide.

Communication

ESP-NOW is Espressif's connectionless protocol that runs directly on the Wi-Fi radio: no association, no DHCP, no router. The boards enable station mode, initialize ESP-NOW and register the other two boards as peers on channel 0 (the current channel). Sending with a null destination address delivers the packet to every registered peer at once, which is how a single scan reaches both other boards.

Events travel as a small fixed-size C struct copied straight onto the wire, avoiding any JSON or other serialization overhead: 

offset  size  type   field  meaning
0       4     int    x      access code parsed from the card
4       4     float  y      reserved, always 0

That is 8 bytes per event, far below the 250-byte ESP-NOW payload limit. The receiving side declares a layout-identical struct and unpacks the incoming bytes with memcpy. Two callbacks complete the picture: a send callback that logs the peer's MAC address together with the delivery status, and a receive callback that logs the byte count and decoded fields. Peer MAC addresses are hardcoded per board; the repository leaves them as placeholders, to be filled in with the values each board reports on the serial console.

Firmware structure

setup() configures the LED pins and the serial console, puts Wi-Fi in station mode, initializes ESP-NOW, registers both callbacks and both peers, and finally brings up SPI, the RC522 and the NDEF adapter. loop() runs the verification sequence above and then waits two seconds before polling again.

The sketch is written so that its transmitter block and receiver block can be dropped independently, depending on the role a given board plays. A sensor-only board, for instance, needs no receive callback. The packet structs are likewise placeholders meant to be swapped for whatever payload a board needs to carry.

Challenges

Settling on a simple struct-based packet format over the other boards' MAC addresses, and the RC522 readers occasionally missing a card scan. The polling cadence is a plausible contributor to the latter: the loop ends with a two-second delay, and a scan adds another 1.5 s of LED time, so a card presented between polls is only picked up on the next pass. Beyond a card-based security system, the same broadcast pattern generalizes to short-range wireless telemetry of any kind, such as distance, temperature or other threshold-based conditions.

Limitations & next steps

Transport security: as a proof of concept, peers are registered with encryption disabled and the access code travels in plaintext, so it could be sniffed and replayed by anyone in radio range. ESP-NOW's per-peer encryption would be the first fix, with a challenge-response or rolling counter on top.

Credential model: every card carries the same access code and card UIDs are logged but not used for authorization. Checking a per-card UID against a table (or a signed token) would allow individual cards to be revoked.

Loop timing: polling and LED timing both rely on blocking delay() calls. Moving to millis()-based scheduling would shorten the polling interval and keep the board responsive while an LED is lit.

Delivery handling: the send result is only logged. Adding retries on failed delivery, and replacing hardcoded MAC addresses with a pairing or discovery step, would make adding a fourth node a configuration change instead of a firmware edit.
